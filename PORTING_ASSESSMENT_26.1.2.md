### Verified transfer API

* `capabilities/Capabilities.java`: block capabilities are `Capabilities.Energy.BLOCK` (`EnergyHandler`, nullable direction) and `Capabilities.Item.BLOCK` (`ResourceHandler<ItemResource>`, nullable direction). Register the same block entities and sided cable provider via the target registration API, preserving exposure and null-side behavior after checking target registration signatures. `EnergyHandler` reports long amount/capacity but `insert(int, TransactionContext)` / `extract(int, TransactionContext)` return int. Capacity is a hint, not proof an insertion succeeds.
* `transfer/transaction/Transaction.java` and `SnapshotJournal.java`: `Transaction.openRoot()` opens a root; `Transaction.open(parent)` opens a child. Closing without commit rolls back; committing a child remains subject to parent rollback. Transactions are thread-bound and a root cannot open inside an existing transaction. Journal `updateSnapshots(tx)` must precede each transactional mutation; snapshot/revert include every mutable piece; `onRootCommit` is for dirty marking and irreversible notification, not immediate correctness. Exceptions before commit normally trigger try-with-resources rollback; exceptions in close/commit callbacks need explicit testing and robust non-throwing callbacks.
* `transfer/energy/EnergyHandlerUtil.java` `move(from,to,amount,tx)` opens a child (or root with null parent), probes extraction in an aborted nested transaction, inserts in the child, extracts exactly the inserted amount, and commits only if equal; otherwise it rolls back. It wraps exceptions in `ReportedException`. For a standalone generator tick, a candidate call is `EnergyHandlerUtil.move(generatorPort, target, remaining, null)`; use the passed context, not null, when already in a transaction. This is an API-grounded example, **not compiled**. A network port's insertion must join that context, including all sinks and budgets.
* `SimpleEnergyHandler` provides snapshot-based storage, per-operation limits and root-commit `onEnergyChanged`; `set()` changes immediately and is not transactional. It serializes an inner lowercase `energy` field, unlike Wool Works' existing top-level `Energy` integer: explicitly preserve/read old format. Separate internal generation/consumption from externally restricted ports, and do not use `set()` while a transaction can roll back. Its per-operation extract limit alone does **not** implement the generator's shared 100 FE/tick output across calls.
* `ItemStacksResourceHandler` and `ResourceHandler<ItemResource>` provide transactional indexed storage with item components, `isValid`, capacity and root-commit change callbacks (`StacksResourceHandler`). Menus use old `ItemStackHandler`/slots and must be migrated too; `transfer/item/ResourceHandlerSlot.java` is a target API entry point. Preserve existing saved inventory encodings explicitly rather than assuming new serializers accept old tags. Automation views must restrict both indexed and generic operations: generator exposes fuel insertion only, extractor exposes input insertion/output extraction while hiding upgrade slot, worker exposes shears/wheat insertion and output extraction only. Keep item identity/components, slot limits and internal machine/menu access distinct. Exercise atomic item moves and rollback; no ported inventory or serialization tested.
* Legacy `IEnergyStorage` and related classes still exist but are deprecated for removal, not the old capability names. `IEnergyStorage.of(EnergyHandler)` wraps target handlers in the **legacy-facing** direction and opens root transactions, so cannot be called within a transactional port. Its `canExtract`/`canReceive` are only capacity-based guesses (`energy/EnergyHandlerAdapter.java`); it is not a safe automatic direction classifier or a general atomic bridge for old handlers.

### Wool Works behavior and proposed migration invariants

* Generator holds 20,000 FE, rejects external insertion and shares 100 FE/tick between all pulls and its own pushes. Extractor holds 20,000, accepts up to capacity per operation and rejects external extraction; worker holds 20,000, accepts up to `Integer.MAX_VALUE` per operation subject to capacity and rejects external extraction. Make the generator tick counter a transaction journal with tick identity and tentative usage visible to subsequent nested calls; rollback restores the counter, root commit makes it durable for the tick. Also test its server/client guard. Keep internal energy use separate from external policy.
* `CableNetworks` caches loaded-chunk BFS topology, invalidates on topology/chunk changes, excludes the source and extraction-facing sinks, uses a reentrancy guard and rotates destinations. Its `used` map is **shared per segment per level per game tick**, not per connection or per route: every successfully routed amount consumes every segment on its selected path. Preserve alternate path search and loaded-chunk checks. Wrap the shared tick/usage and any rotation changes in a journal: reserve budget immediately in the current transaction so subsequent branches, calls and nested transfers see it; rollback must restore it at every depth. Deferring all budget updates until root commit allows bypass; charging during simulation without rollback loses throughput. Tick rollover and topology invalidation while a transaction is open need explicit safe handling/tests, not an assumed solution. Do not rely on object identity alone to identify the same external storage when providers can return distinct wrappers.
* For passive pushes, cable `insert(amount, tx)` routes into destination `insert` calls in that same transaction, journaling segment reservations; the outer caller must debit its source atomically, as `EnergyHandlerUtil.move` does. Preserve recursion guard without blocking legitimate child operations. For active pulls, call `move(source, cablePort, rate, null)` from the server tick, so source, destination(s), generator quota and cable budget commit or roll back together. Pending legacy cable energy must be treated as an already-debited saved balance, transactionally delivered and decremented exactly once; retain `PendingEnergy`/`PendingSide` and break/item preservation until migrated balances are drained. Do not manufacture a new source debit for those balances.
* `CableBlock.setPlacedBy` currently auto-enables extraction only for `canExtract && !canReceive`; shears toggle sides manually; active tick clears a side when the neighbor is not extractable. Target `EnergyHandler` has **no** direction-support query (`energy/IEnergyStorage.java` explicitly says no equivalent). An aborted one-unit probe only observes current state: empty producers and full consumers cannot be classified reliably; zero results do not establish permanent inability. Therefore exact generic preservation is not achievable from this API alone. Investigate an explicit interoperable direction hint or documented policy/fallback, and require a decision before claiming equivalence; do not silently clear manually configured empty sources or auto-enable arbitrary bidirectional storage based on a failed probe. Retain `ExtractionMask`, manual control and existing placement-data behavior. This is an unresolved compatibility risk, not verified equivalent behavior.
* Validation gates: account for source + sink + pending balance across partial acceptance, exact-extraction failure, exceptions, simulated child abort, committed child/aborted parent, multiple pushes/pulls, branched/cyclic networks, shared bottlenecks, per-tick rollover and different capability wrappers; test topology invalidation and chunk unload without forced loads. Also test old-world energy/inventory and broken/replaced cable item migration, empty/full and bidirectional neighbors, external compliant handlers, and present/absent JEI/Jade on dedicated server. None of these target tests has run.
